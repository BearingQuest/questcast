# Decisions

Owner decisions for QuestCast (formerly XGeneratePosts), newest last. The v3 design brief
(provider abstraction) holds the full reasoning; this log records what was
decided, when, and where it departs from the baseline.

| Date | Decision | Why |
|---|---|---|
| 2026-10-20 | **Default provider is Groq; Anthropic stays selectable, unchanged.** `--provider` / `AI_POST_PROVIDER` choose `anthropic`, `groq` or `openai-compat`. | The paid Anthropic key predates the $0 rule. Groq was the only free option covering both the model and the search in one call. The provider abstraction, not the provider, is the protection if a free tier ends. |
| 2026-10-20 | **No search-API source.** Search sources are `native` (the provider searches server-side) and `rss` only. | A third source would add a second vendor, key and free tier for a capability the two paths already cover. The search interface stays open to add one later. |
| 2026-10-20 | **Baseline conversion deferred to v3.1** (departure recorded). v3 does not adopt: uv with a committed lockfile, Typer, Pydantic settings, mypy strict, 85% coverage, `make check` / `make audit`, packaging and release. | v3 is scoped to the provider work plus tests, CI and LICENSE. Until the lockfile lands, CI pins pytest 9.1.1 and resolves its dependencies with `uvx --exclude-newer 2026-10-20`. |
| 2026-10-26 | **Groq model is `openai/gpt-oss-120b` with the `browser_search` tool** (`tool_choice: required`, `reasoning_effort: low`), overridable with `GROQ_MODEL`. Replaces `groq/compound`. | Groq deprecated `groq/compound` and `groq/compound-mini` on 24 Aug 2026 and shut them down on 21 Sep 2026 with no replacement named ([deprecations](https://console.groq.com/docs/deprecations)). Browser Search on GPT-OSS is Groq's documented server-side search ([browser search](https://console.groq.com/docs/browser-search)). Unconfirmed until the first live run: whether the free plan allows `browser_search`, and whether one call fits its 8,000 tokens-per-minute limit. If either fails, run `--provider groq --search rss` and revisit the default. |
| 2026-10-26 | **R20: separate timeouts.** Feed requests 15 s. Provider calls default 120 s via `AI_POST_PROVIDER_TIMEOUT`, which applies to `groq` and `openai-compat` only; the Anthropic SDK keeps its own default. | 15 s is too short for a server-side browser search. Anthropic stays unchanged, and its web search can run long too. |
| 2026-10-26 | **R21: RSS requires Expat 2.7.2 or newer.** Below that, `--search rss` exits naming both versions, and the RSS tests fail rather than skip. | Python's docs say Expat below 2.7.2 may be open to billion-laughs, quadratic-blowup and large-token attacks ([XML security](https://docs.python.org/3/library/xml.html#xml-security)). CI must not pass silently without the RSS tests. |
| 2026-10-26 | **Lint exceptions: `noqa: S310` and `noqa: S314`, each with its reason inline.** S310 on `urllib.request.Request` where the scheme is checked first (https only; plain http only for a localhost openai-compat server). S314 on `xml.etree.ElementTree.fromstring`, behind the Expat check. | R5 allows only the standard library, so `defusedxml` is not an option. Expat 2.7.2+ limits entity amplification and never fetches external resources. Feeds are also capped at 10 MB (R23), and only `identity` encoding is requested (urllib's default), so nothing is decompressed. |
| 2026-10-27 | **R23: feeds get their own 10 MB size cap** (`MAX_FEED_BYTES`). Provider responses keep the 2 MB cap (`MAX_RESPONSE_BYTES`). | In the first live runs, the PostHog and CNCF feeds were over 2 MB and got skipped. |
| 2026-10-27 | **R22: rank and cap RSS candidates.** After the per-feed cap (R19), candidates are ranked by how many distinct topic words (lower-cased, 3+ letters, stop words removed) appear in the title or summary, ties newest first and undated last. At most `AI_POST_RSS_MAX_ENTRIES` are sent (default 20, a whole number of 1 or more). | On 27 Oct, 63 unfiltered candidates plus the profile came to 12,874 tokens, against Groq's free limit of 8,000 tokens per minute, and the call failed with HTTP 413. |
| 2026-10-27 | **R24: 413 and 429 get separate messages** (`groq` and `openai-compat`). 413 says the request is too large for the plan's per-minute token limit and doesn't suggest waiting. With `--search rss` it suggests lowering `AI_POST_RSS_MAX_ENTRIES` or `AI_POST_RSS_PER_FEED`; with native search, `--search rss` with a smaller `AI_POST_RSS_MAX_ENTRIES`. 429 says to wait, with the server's retry-after value when given, and mentions `--search rss` only in native mode. The Anthropic messages are unchanged. | On 27 Oct a 413 told the user to wait and re-run, which can't help a request that is over the limit on its own. Anthropic's 413 is a request-size limit, not a token rate, and R11 keeps Anthropic unchanged. |
| 2026-10-27 | **argparse, not Typer** (departure from the baseline). | The runtime stays standard library only (v3 R5, v3.1 brief section 1). Typer would be the only runtime dependency, for a CLI with a handful of flags. |
| 2026-10-27 | **A small standard-library config module, not pydantic-settings** (departure). One module will read every environment variable in one place; it lands in v3.1 PR 2 with the package. | Same reason: no runtime dependency, nothing at runtime for pip-audit to flag, and the install stays trivial. |
| 2026-10-27 | **`print` for command-line output, not structured JSON logging** (departure). `print` is already a ruff per-file exception (`T201` in `daily_post.py`); `run.log` stays one plain-text line per run. | A personal CLI's output is read by a person, and nothing machine-reads the log. |

| 2026-11-03 | **R51: wait and retry once on 429** (`groq` and `openai-compat`). The suggested wait comes from the `retry-after` header (seconds), else "try again in N(.N)s" in the body. If it is at most `AI_POST_RATE_LIMIT_WAIT` (default 60 s, read at call time, 0 turns it off), the run waits that long plus 1 s and sends the same request once. A second 429, a longer wait, no wait, a 413 and every other error stop with the R24 message, with one more line when the wait was over the setting. Groq's other wait forms ("1m30s", "450ms") and an HTTP-date `retry-after` aren't parsed, so they aren't retried. Anthropic is unchanged. | On 3 Nov a native run got a 429 on the per-minute token limit ("Used 5473, Requested 6153 … try again in 27.195s"), and the only remedy was to re-run by hand. One bounded retry covers a per-minute limit; a daily limit's wait is far over 60 s, so it still stops. |
| 2026-11-03 | **R52: progress on stderr.** One helper (`progress.status`) covers both the R51 countdown and the wait for the provider's answer (all three providers). On a terminal, a daemon thread redraws one line about once a second and, on success, error or Ctrl+C, stops and clears it; otherwise a start and an end line are printed and no thread runs. Never written to `run.log`. Ctrl+C keeps its "Cancelled." exit. | A server-side search can take a minute or more, and a 27 s wait with no output looks broken. Off a terminal (the acceptance tests, a scheduled run) a ticker would fill the log with redraws. |
| 2026-11-03 | **R53: token budget for `--search rss`, default 7,000 estimated tokens** (`AI_POST_TOKEN_BUDGET`). Estimate: UTF-8 bytes / 4, rounded up, standard library only. After ranking and the R22 cap, the lowest-ranked entries are dropped until the whole prompt fits, and the run says "Sending N of M feed entries to fit the token budget". If no entry fits, it stops with the size of the profile sections sent. The `run.log` OK line records the provider's `usage` counts when given. | Measured on 3 Nov, with 36 history entries and 20 realistic entries of about 590 bytes each: the example profile's prompt is 24,965 bytes, an estimate of 6,242, so all 20 are sent. Groq would count about 5,920, at the 4.22 bytes per token it reported for the real rss request. The 3 Nov 413 used Dusten's 15.6 KB profile, whose prompt with 20 entries is about 35,200–36,000 bytes, an estimate of 8,811–8,996, against Groq's reported 8,344, so the estimate over-counted by about 6%. With no entries that prompt is already 6,039; 7,000 keeps 6 entries (an estimate of 6,928), which Groq would count at about 6,570, some 1,400 (18%) under the 8,000 limit. 7,000 leaves 1,000 tokens for the chat template and for feed text (URLs especially) that tokenizes denser than 4 bytes a token. The usage figures will show whether to adjust `BYTES_PER_TOKEN` or the default. Later on 3 Nov the prompt's lists of used URLs and titles were capped at the newest 20 each (`PROMPT_USED_LIMIT`, was 60): each history entry adds about 43 estimated tokens to every prompt until the cap, so at 60 the rss prompt would have passed the budget on its own after about 24 more runs; dedup is unchanged, since `is_used` checks a pick against the whole history and rss candidates are filtered against it before sending. With the cap, the same measurement keeps all 20 entries for the example profile (an estimate of 5,395) and 12 of 20 for Dusten's (6,964). |
| 2026-11-03 | **R54: clean provider error text** (`groq` and `openai-compat`). | 2026-11-03 | **R55: credentials never follow a redirect to another origin.** `net.NoDowngradeRedirectHandler` still refuses HTTPS to HTTP first (R18, same message), then removes `Authorization` and `Proxy-Authorization` from the redirected request when the origin changes. Origin is the scheme, the lower-cased host and the port, with 80 and 443 filled in; a port that won't parse counts as another origin. A same-origin redirect keeps both. Covers every `net.HTTP_OPENER` caller: `groq`, `openai-compat`, feeds and, from R56, LinkedIn. Out of scope: the X path (tweepy) and the Anthropic SDK do their own HTTP. | Python 3.14's `HTTPRedirectHandler.redirect_request` copies every header in `req.headers` except Content-Length and Content-Type to the new request, whatever its host (found in review on 27 Oct); `add_header` stores names `capitalize()`d, so the removal uses `"Authorization"` and `"Proxy-authorization"`. `ProxyHandler` re-adds Proxy-Authorization for every request whose target is proxied, so removing it matters only when the target bypasses the proxy (`no_proxy`), which is exactly when it must not be sent. Cookie needs nothing: the opener has no cookie handler and nothing sets one. The rule matches the requests library's. |
| 2026-11-03 | **R56: LinkedIn publishing uses the shared opener.** `post_to_linkedin` sends through `net.HTTP_OPENER` with a fixed 30 s timeout (`config.LINKEDIN_TIMEOUT`) and reads the response through `net.read_capped` (2 MB); the error body read is bounded at 4,000 bytes. Existing messages are unchanged. An oversized response or a read timeout gets a new message saying LinkedIn may already have published the post. The Semgrep suppression on the old `urlopen` call is removed (see its row). | The bare `urlopen` had no redirect check, no size cap and no timeout. The timeout is fixed rather than `AI_POST_PROVIDER_TIMEOUT`: that one is sized for server-side model search (120 s) and documented as applying to `groq` and `openai-compat` only, while a single REST POST should answer in seconds. Both new failures can come after LinkedIn accepted the post, so the message warns before a re-run makes a duplicate. |
| 2026-11-05 | **R58: say why a reply had no text** (`groq` and `openai-compat`). Shown strings have line breaks and control characters (including U+2028/U+2029 and U+0085, which `str.splitlines` splits on) replaced with spaces, then get the R54 cleaning and key redaction, at most 40 characters each, so the FAILED line stays one line whatever the reply's shape. No retry. | On 5 Nov two rss runs a minute apart failed "groq returned no text for model openai/gpt-oss-120b", and the log couldn't say why. The reasoning page says the default completion limit "may be too low for complex reasoning", which suggests reasoning can use up the limit but doesn't say so.
